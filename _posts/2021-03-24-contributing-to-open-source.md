工作好几年了还没有成为一名开源贡献者，实属失败。最近进行了人生中第一次给开源项目贡献代码，记录一下。

**温馨提示：文章较长，不想听我啰嗦的，可以直接看最后的总结。**

## 背景

作为一个技术开发者，怎么能没有属于自己的技术博客呢？我很荣幸选择了一个优秀的开源博客项目：[Hexo](https://github.com/hexojs/hexo) 和一个 Hexo 主题：[hexo-theme-next](https://github.com/theme-next/hexo-theme-next)。因为其源码是 Node.js 写的，恰好我也是写 Node 的，所以在使用过程中有一些疑问、Bug 或需求时，我能够简单读懂和修正。这次贡献代码的项目就是 Theme NexT。

## 贡献历程

没有经验的我，第一步是从 GitHub 把项目 clone 到本地，然后创建了一个新的分支，接着就开始写代码。一顿操作之后，终于 coding 完成！下面是 Git 常规提交代码流程：`git add`、`git commit`（按照我们开发规范，参照 Angular commit message 格式）。

**踩坑开始。** `git push` 的最后一步执行 `git push origin branchname`，报错：`No permission`。此时，蒙圈中……回过神来：

第一步：为什么远程分支不让提交？我想起我们的项目只有参与者才能贡献代码，于是查看了一下项目成员。其实这完全属于瞎想，扭头拍下脑袋，不对，这不是开源项目吗？不可能只有参与者才能提交，于是否定了自己。

第二步：无计可施，面向 Google 吧。然后找到秘籍：[如何给开源项目贡献代码？](https://gist.github.com/zxhfighter/62847a087a2a8031fbdf)。看的过程中，马上回忆起以前同事给我说过：**先从源项目 Fork 一份到自己的 GitHub 仓库中，然后在自己的分支下编写代码并提交，重复上面的代码提交流程。** 这次提交成功了，很是欣喜。到这时已经鼓捣半小时了，认真起来的我看到了效果，满怀激动，接着干。

第三步：创建 PR（New pull request）。Commit message 都仔细、小心地选择英语单词和短语。当我提交的那一刻，弹出了一些列表：

![开源项目 Pull Request 检查清单](/assets/img/posts/zhihu-359612351/image-001.png)

对于英文不是很好的我，这又是一个绊脚石。不过还好关键词都认识，一边猜一边翻译，大概也知道都要做些什么了：

- 改变选择状态，将 `[ ]` 变成 `[x]`。点了一下旁边的 Preview 预览效果，不错，变成 ☑️ 了。
- 是否对你所做的 Bug 修复或新功能进行了测试。下面两个不知道是什么测试，仓库中没有单元测试，不过官方有测试文档。我按照文档测试了一下，并且在自己的项目中进行了测试和发布，所以几乎可以确保没有问题。
- Commit message 是否按照规范格式书写，然后给出一个文档。接下来又是一顿读文档，读完之后发现跟我平时的提交代码规范差不太多，只是更换为首字母大写，type 多了几种。
- 是否在官方使用文档中添加了你的修改，然后给出一个链接。这个链接是专门放文档的仓库，里面放着各类说明文档、使用文档和第三方文档等。我按照规定修改了文档并提交 PR，过程中还要签一份协议，邮箱会发来一个链接，授权签完之后，文档这块算是处理完了。
- 回过头来继续看下面的 PR Type。我选择了 Feature，因为没有更合适的 type 了。
- 当前版本是多少？我没有填，因为后来才注意到，也觉得没那么重要，就忽略了。
- 新版本修改吗？没有填，理由同上一条。
- 如何在配置中使用？给出一个代码块，我填写了使用方式。

最后给上一张完成的截图。

最最后一步，一键 Create，大功告成！费了这么久工夫，终于完成，小激动。

## 总结

1. 从 GitHub 官方开源项目 Fork 一份到自己的仓库
2. `git clone` 到本地
3. Coding
4. 提交代码
5. 创建 PR 到官方仓库
6. 等待 Approve and merge
