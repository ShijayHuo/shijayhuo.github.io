## 引言

最近在迁移博客时，看到了一篇来自前同事的分享。它大约整理于 2023 年，时至今日再读，发现其中很多内容依然适用，所以也借这次迁移重新温故一下。

AI 出现后，工作中的协作角色和模式都发生了变化。过去我们主要和人协同，现在更多时候也在和 AI 协同。但无论协作者是谁，目标并没有变：开发出好的、可维护的软件。

这些注意事项和工程规范，既可以约束人，也可以转达给 AI。AI 出现，并不意味着可以从此随意梭哈，让它自由发挥。代码迟早还是要有人读、有人判断、有人负责。

否则，流程很容易变成：AI 写代码，出了问题再问 AI，AI 继续解释和修复；人只负责描述需求与 Bug 现状，却不再关心 AI 做得如何、为什么这样做、有没有真正理解并对齐需求。说白了，问题最终还是落在你对代码有没有把控。

人以后是否会彻底不再读代码？这件事我不敢妄言，也许真有那么一天。但至少在现阶段，我仍然建议人保有这些工程意识，并把它们清楚地传达给 AI。

## 一、混乱的代码

### 如何产生

- 照本宣科，无封装，无设计
- 代码结构混乱
- 命名太随意，看到方法名不知道要做什么
- 文件职责不明确，相互调用
- 继承一切
- 单个函数接收参数过多或做了很多件事情
- 单文件特别大
- 底层架构不牢固，牵一发而动全身

### 代价

- 初期进展迅猛，2 年后进展如蜗牛，甚至要重头改造
- 改动代价太大，本该很快完成的工作需要很久才能完成
- 修复一个缺陷造成其他缺陷
- 扩展性较差，产品升级成本高
- 新人学习和改造成本高
- 性能较差，很难优化

### 解决

- 统一技术栈
- 引入框架
- 封装底层库
- 统一代码及代码结构规范
- 培训
- Code Review
- 其他

## 二、重复造轮子

- 组件库有组件可以直接用
- 组件库有组件需要改造
- 组件库无组件，可以封装起来
- 已经有通用的 API
- 可以抽象成通用 API
- 业务代码无抽象
- 工具函数无抽象
- 相似的实体未抽取父类
- 只有一个字段不同的表，如果可能就放在一个表里，加一个类型区分；硬拆成两个表，就不得不在代码中重复
- 其他

## 三、过度设计

- 为了设计而设计，过度追求模块化、可扩展性、设计模式等
- 考虑的场景很全，实际上很多场景不会出现
- 简单的业务启动太多服务，造成资源浪费

## 四、低估工作量

- 拍脑袋给一个时间
- 对业务理解不够
- 忽略业务场景
- 没有技术调研
- 没考虑封装
- 团队沟通成本
- 调试时间
- 测试时间
- 验收与交付

## 五、无测试

- 单元测试
- 接口测试
- 集成测试
- 测试覆盖
- 边界值测试：只测试常规场景，忽略用户行为

## 六、糟糕的代码提交

### 分支

- 在错误的分支提交代码
- Hotfix 代码没有同步到目标版本的分支上

### Commit

- 糟糕的描述，如 `feat: add`、`fix: fixed some error`
- 不遵守提交规范，如 `feat`、`refactor`、`fix`、`style`、`test`、`chore`
- 多个功能一次 Commit

## 七、做了很多无用的工作

- Copy 很多无用的代码，然后删减
- 过度学习
- 技术调研偏离轨道
- 框架已有的 API，自己重新实现了一套
- 基础库已经封装的功能，自己重新实现一套

## 八、必要注释

- 复杂功能无注释
- 有注释，但是没有标出有效信息
- 整段代码被注释，无说明

## 九、日志中没有记录任何相关信息

- 错误日志没有堆栈信息
- 记录无用的日志，比如 `console.log("")`
- Info 日志混乱，使用各种格式记录

## 十、忽略性能

- 使用递归造成死循环
- 数组循环套循环
- 内存计算没考虑内存泄漏风险
- 循环操作 IO
- 必要的时候要知道使用缓存
- 数据库无索引
- 查询条件复杂
- 全量查询

## 十一、其他

- 独占信息
- 口头说明不如一篇有效的文档或说明信息
- 埋头苦干
- 目标不清晰
- 跟产品讲技术，你考虑过产品的感受吗
