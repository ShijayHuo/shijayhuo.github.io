## 背景
最近参与开发的项目上线了。由于是新团队、新项目，很多规范尚未建立，这次部署和发版就遇到了版本号的问题。

产品本次发布的版本是 `v1.0.2`。由于前期公网环境和测试环境共用一套环境，测试发现 Bug 后，需要频繁修复并重新发版，而代码发布使用的 Tag 是 `v0.2.2`。于是，一个项目里出现了产品版本号和代码 Tag 两套编号。

根据过往经验和之前公司的做法，产品版本号通常与代码 Tag 保持一致，所以我下意识觉得这件事不太对。我把问题提给同事，有人认为代码修复和发版太频繁，肯定无法与产品版本号对应；也有人觉得无所谓，只要不是一串提交哈希就行。

但我觉得版本规范不该如此含糊，所以，下面就来掰扯掰扯这个问题。

## 版本号的意义

一款产品需要持续迭代和发布。每次发布都会形成一个产品快照，这个快照可以称为一个**版本**。为了区分不同版本，就需要为它们分配编号，也就是**版本号**。

版本号的作用主要有两点：**一是记录产品演进和发布里程碑，二是方便回溯与沟通**。例如，团队经常会讨论某个功能在哪个版本上线；用户遇到问题时，也可以提供版本号，帮助开发人员快速定位当时的功能和运行环境。

## 产品版本号和代码版本号不是一回事

> P.S.：这里的代码版本号，特指代码版本标识——GitHub Release 中的 Git Tag。

因为二者往往都使用 `x.y.z` 的形式，很容易在潜意识里把它们混为一谈。之前公司也一直让两者保持一致，我自然也不例外。

严格来说，**产品版本号主要用于表达产品功能和兼容性的变化，而 Git Tag 用于标识该次发布对应的源码快照**。

## 产品版本号和代码版本号需要一致吗？

先说结论：**概念上二者不必相同，但对于正式发布，推荐让产品版本与 Git Tag 保持一一对应**。

我们代入一下实际情况：产品经理反馈，用户使用 `v1.0.2` 时遇到了某个 Bug。开发人员要复现并定位问题，就需要找到该版本对应的代码。**这里的关键，是如何准确找到产品版本对应的源码快照**。根据两者是否一致，可以分为两种情况：

1. 产品版本号与 Git Tag 不一致
2. 产品版本号与 Git Tag 一致

如果二者不一致，就需要额外维护映射关系，例如产品版本 `v1.0.2` 对应 Git Tag `v0.0.2`，产品版本 `v1.0.3` 对应 Git Tag `v0.0.8`。随着版本增加，查询和维护的成本也会越来越高。

反之，如果二者一致，就可以直接通过产品版本号找到对应的 Git Tag，不需要额外查询。更重要的是，这种简单明确的规则更容易让团队建立共识。

![产品版本号与 Git Tag 一一对应可以简化问题回溯](version-mapping-v5.png)

另外，不少成熟的开源项目也采用产品版本与 Git Tag 一一对应的方式，例如：

| 企业/项目 | 产品发布版本 | Git Tag | 链接 |
|---|---|---|---|
| Microsoft .NET | `.NET 10.0.10` | `v10.0.10` | [.NET Runtime Release](https://github.com/dotnet/runtime/releases/tag/v10.0.10) |
| GitHub CLI | `GitHub CLI 2.97.0` | `v2.97.0` | [GitHub CLI Release](https://github.com/cli/cli/releases/tag/v2.97.0) |
| HashiCorp Terraform | `v1.15.8` | `v1.15.8` | [Terraform Release](https://github.com/hashicorp/terraform/releases/tag/v1.15.8) |
| Kubernetes | `v1.36.3` | `v1.36.3` | [Kubernetes Release](https://github.com/kubernetes/kubernetes/releases/tag/v1.36.3) |

## 版本号的命名规则

很多软件项目采用 `x.y.z` 形式的版本号。只有当三个数字分别按照主版本、次版本和修订版本的兼容性规则递增时，才能称为语义化版本（Semantic Versioning，SemVer）。具体规范可以参考👉 [Semantic Versioning 2.0](https://semver.org/)。

回顾之前公司的做法，大致是：

- 产品有自己的 Roadmap，每次迭代都会对应一个发布计划。迭代开发完成、代码和产品发布之前，由产品经理申请一个版本号，例如 `v1.0.2`，后续发布都围绕该版本号进行。
- 开发人员拿到版本号后，以该版本号创建 Tag，例如 `v1.0.2`。
- 遇到特殊发布场景时，团队会在基础版本后增加约定的后缀，形式与 [Semantic Versioning 2.0——版本优先级排序](https://semver.org/lang/zh-CN/#spec-item-11) 中的预发布标识类似：
  - 正式发布前需要多次构建时：
  ```bash
   # Tag 使用版本号加时间戳
   tag: v1.0.2-202608042000
  ```
  - 某次独立构建仅用于特定环境时：
  ```bash
  # Tag 使用版本号加环境
  tag: v1.0.2-alpha、v1.0.2-beta、v1.0.2-rc、v1.0.2-prod
  ```
  - 需要同时标记环境和构建时间时：
  ```bash
  # Tag 使用版本号加环境和时间戳
  tag: v1.0.2-beta-202608042000
  ```
  - 为某个历史版本制作 Hotfix 时：
  ```bash
  # 使用原版本号加时间戳和 Hotfix 标识
  tag: v1.0.2-202608042000-hotfix 
  ```
  - 对于需要长期迭代的大版本：
  ```bash
  # Tag 使用版本号加 next 和序号
  tag: v1.0.2-next.1
  ```
- 上述后缀只用于独立构建。多数情况下，同一份构建产物会在多个环境间逐级晋级，此时应复用同一个 Tag，不再按环境重复创建 Tag。
- 如果要在某个特定版本上新增功能，就属于新的功能迭代，应申请一个不冲突的新版本号，再沿用上述 Tag 规则。
```
生成候选构建，Tag：v1.0.2-202608042000
        ↓
部署 Alpha
        ↓
部署 Beta
        ↓
部署 Rc
        ↓
确认正式版本，Tag：v1.0.2
        ↓
部署 Production
```

## 总结

- 产品版本号描述产品功能和兼容性，Git Tag 标识该次发布对应的源码快照。
- 正式发布时，推荐让产品版本与 Git Tag 一一对应，例如产品 `v1.0.2` 对应 Tag `v1.0.2`。
- 同一构建在多个环境间逐级晋级时复用同一个 Tag；独立构建、预发布或 Hotfix 则使用统一的后缀区分。

最后，你们团队目前是如何做的，欢迎讨论。
