## 背景
最近，上线一个新项目，在部署打 tag 定版本号上和同事产生了分歧，具体情况是这样：

第一次上线时，产品和开发是没有约定的，产品的角度定的版本号是从 v1.x.x 开始的，而技术这边是从 v0.x.x 开始打 tag 的，于是，同一个项目里出现了两套编号。

按我过去的经验，产品版本号通常会和代码 Tag 保持一致，在后面几次修复bug再上线时，我观察到存在两套版本号，潜意识告诉我这肯定是有问题的，然后我提出这个问题，同事 A 觉得，修 Bug 和发版这么频繁，根本没法和产品版本号一一对应；同事 B 有点和稀泥的意思，说 Tag 怎么命名都行，只要不是 sha256（哈希）就行。

明知不合理，后面排查问题肯定比较费劲，但我的嘴被堵住了......所以，我应该先把最佳实践以及背后的知识整理一下，后面形成共识。

## 版本号的意义

产品不会只发布一次。每发布一次，产品就会形成当时的一张快照。这张快照就是一个**版本**。为了方便团队协作沟通，就需要有一个称谓：**版本号**。

说到底，版本号主要解决两个问题：**一是记录产品演进和发布里程碑，二是方便回溯与沟通**。比如，某个功能是哪个版本上线的？用户反馈的问题发生在哪个版本？只要版本号说清楚了，开发人员就能更快地还原当时的功能状态和运行环境。

## 产品版本号和代码版本号不是一回事

> P.S.：本文说的代码版本号，特指代码版本标识——GitHub Release 中的 Git Tag。

两者往往都长成 `x.y.z` 的样子，看起来就像一回事。再加上之前公司一直让两者保持一致，我潜意识也没有做过严格区分。

但严格来说，它们的职责并不一样：**产品版本号主要表达功能和兼容性的变化，Git Tag 则用来标记这次发布对应的源码快照**。

## 产品版本号和代码版本号需要一致吗？

先说结论：**从概念上说，二者不必相同；但到了正式发布时，最好让产品版本和 Git Tag 一一对应**。

比如，产品经理反馈：用户在 `v1.0.2` 里遇到了一个 Bug。开发人员想复现问题，第一步就是找到 `v1.0.2` 当时用的代码。**所以真正关键的，是能不能准确找到产品版本对应的源码快照**。这里无非有两种情况：

1. 产品版本号与 Git Tag 不一致
2. 产品版本号与 Git Tag 一致

如果二者不一致，团队就得另外记下它们的对应关系。比如，产品版本 `v1.0.2` 对应 Git Tag `v0.0.2`，产品版本 `v1.0.3` 对应 Git Tag `v0.0.8`。版本少时可能还记得住，版本一多，查起来和维护起来都会越来越麻烦。

如果二者一致，事情就简单多了。看到产品版本号，就能直接找到同名的 Git Tag，中间不需要再查一层对应关系。而且规则足够简单，团队也更容易达成共识。

![产品版本号与 Git Tag 一一对应可以简化问题回溯](version-mapping-v5.png)

这种做法并不少见。很多成熟的开源项目也会让产品版本和 Git Tag 一一对应，例如：

| 企业/项目 | 产品发布版本 | Git Tag | 链接 |
|---|---|---|---|
| Microsoft .NET | `.NET 10.0.10` | `v10.0.10` | [.NET Runtime Release](https://github.com/dotnet/runtime/releases/tag/v10.0.10) |
| GitHub CLI | `GitHub CLI 2.97.0` | `v2.97.0` | [GitHub CLI Release](https://github.com/cli/cli/releases/tag/v2.97.0) |
| HashiCorp Terraform | `v1.15.8` | `v1.15.8` | [Terraform Release](https://github.com/hashicorp/terraform/releases/tag/v1.15.8) |
| Kubernetes | `v1.36.3` | `v1.36.3` | [Kubernetes Release](https://github.com/kubernetes/kubernetes/releases/tag/v1.36.3) |

## 版本号的命名规则

我们常见的版本号，大多长成 `x.y.z` 的样子。不过，用了这个形式，不代表它就是语义化版本（Semantic Versioning，SemVer）。只有三个数字分别按照主版本、次版本和修订版本的兼容性规则递增时，才能叫 SemVer。具体规范可以参考👉 [Semantic Versioning 2.0](https://semver.org/)。

回顾了我之前公司的做法，大致是这样：

- 首先，产品会有一个整体的 Roadmap，由多个里程碑和小版本节点组成，每次迭代都对应一个发布计划。迭代开发完成后，产品经理会在正式发布前申请一个版本号，比如 `v1.0.2`。后面的发布都围绕这个版本号进行。
- 版本号定下来后，开发人员会用同一个版本号创建 Tag，比如 `v1.0.2`。
- 碰到特殊的发布场景，团队会在基础版本后面加上约定好的后缀。它的形式和 [Semantic Versioning 2.0——版本优先级排序](https://semver.org/lang/zh-CN/#spec-item-11) 中的预发布标识类似：
  - 正式发布前需要多次构建时：
  ```bash
   # Tag 使用版本号加时间戳
   tag: v1.0.2-202608042000
  ```
  - 某次独立构建仅用于特定环境时：
  ```bash
  # Tag 使用版本号加环境
  tag: v1.0.2-alpha、v1.0.2-beta、v1.0.2-rc、v1.0.2-prod
  ```
  - 需要同时标记环境和构建时间时：
  ```bash
  # Tag 使用版本号加环境和时间戳
  tag: v1.0.2-beta-202608042000
  ```
  - 为某个历史版本制作 Hotfix 时：
  ```bash
  # 使用原版本号加时间戳和 Hotfix 标识
  tag: v1.0.2-202608042000-hotfix 
  ```
  - 对于需要长期迭代的大版本：
  ```bash
  # Tag 使用版本号加 next 和序号
  tag: v1.0.2-next.1
  ```
- 这些后缀只用于独立构建。更常见的情况是，同一份构建产物从一个环境逐步晋级到下一个环境。这时直接复用同一个 Tag，不再为每个环境重复创建 Tag。
- 如果要在某个版本上增加新功能，那就算一次新的功能迭代。这时需要申请一个不冲突的新版本号，再继续使用上面的 Tag 规则。
```
生成候选构建，Tag：v1.0.2-202608042000
        ↓
部署 Alpha
        ↓
部署 Beta
        ↓
部署 Rc
        ↓
确认正式版本，Tag：v1.0.2
        ↓
部署 Production
```

## 总结

- 产品版本号说明产品功能和兼容性的变化，Git Tag 则标记这次发布对应的源码快照。
- 正式发布时，最好让产品版本和 Git Tag 一一对应，比如产品 `v1.0.2` 对应 Tag `v1.0.2`。
- 同一份构建产物在多个环境之间逐步晋级时，复用同一个 Tag 就行。独立构建、预发布或 Hotfix，则用统一的后缀来区分。
