“我写的代码没有 Bug”“公司没有规定，个人没这个习惯”“场景复杂，没法测试”“过于麻烦”“没必要”“太痛苦”……这些字眼成为了我这些年来不写测试的理由，或者说借口。

归根到底，一方面是自己的懒惰，另一方面是没有从内心认识到测试真正带来的收益。下面记录我在写测试过程中的思路、认识、理解和感悟。

## 从测试目标开始

写测试时，首先要确定：**我想测什么？**

是 API 测试还是功能测试？再具体一点，是哪些 API、哪些功能？确定目标后，伴随而来的下一个问题是：**怎么测？**

思考“怎么测”时，我会站在使用者的角度，包括产品用户和调用 API 的开发者。我期望输入什么、执行什么操作，又应该得到什么结果？

## 测试驱动开发

一次与同事交流时，他提到了测试驱动开发。什么是测试驱动开发？简单说，就是在具体开发之前，先把要验证的测试用例列出来。这里的测试用例就是接下来要开发的功能，然后用实现代码逐步让测试通过。

![TDD 测试驱动开发循环](/assets/img/posts/yuque-mxdqie/image-003.png)

我尝试之后发现，在一些情况下这种方式很不错，相当于在开发之前先写了一遍 TODO。不过有时一个功能需要执行一连串操作或复杂逻辑，其中一些场景和细节只有在开发过程中才会发现，这时也可以先开发功能再补测试。

当测试写得多了、开始得心应手，先写还是后写可以根据场景选择。

## 测试也需要质量

测试本身也要有质量，尽量抽象和复用。无用的测试只是在瞎胡闹、掩耳盗铃，与写测试的初衷相悖。

例如要测试“根据年龄、身高和学历过滤用户”的 API，可以先随机创建几个具有不同条件的用户，然后组合过滤条件，并明确期望返回哪些用户。结果符合预期则通过，反之失败。

## 测试带来的收益

写测试会花费时间和精力，但它也能带来长期收益：

1. **为重构兜底。** 重构时很难仅靠人工判断是否影响了其他引用。有测试后，一键运行就能暴露问题，让代码修改更有信心。
2. **发现遗漏场景。** 测试会暴露开发时没有想到或没有覆盖的边界，帮助我们及时调整。
3. **加深对功能的理解。** 从输入、行为和结果重新审视功能，会产生新的思路。
4. **让代码更可信。** 测试不能证明代码绝对没有问题，但能让重要行为得到持续验证。

最后，建议让代码带上重要的一环：测试。也提醒自己，再忙、再着急，也要把重要测试补全并坚持下去。
