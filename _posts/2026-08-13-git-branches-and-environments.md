## 分支和环境的区别

> 见过很多开发混淆这个的......

先说下两者的作用，**Git 及分支是用来管理代码的，环境是执行代码变成可用软件的。**它们之间会发生联系，是因为代码最终要部署，中间还隔着构建代码这个环节呢。

```text
分支 / Tag
    ↓ 选择某个 Commit
   CI 构建
    ↓
构建代码快照
    ↓ 加上当前环境的配置
Dev / Test / Staging / Production
```
## 它们是干嘛的？

这里简单回顾一下分支部分：

开发一个新功能时，我们从某条基线创建 `feature/*`，目的是把这次代码修改隔离出来；多个功能进入 `develop`，目的是形成下个版本的集成状态；到了发布节点创建 `release/*`，目的是固定这次版本的代码范围；`main` 则保存已经正式发布的代码状态。

所以，分支主要解决下面几个问题：

1. 我应该基于哪段代码开始修改？
2. 多个人的修改怎样合在一起？
3. 哪些代码属于这次发布？
4. 线上版本出现问题，应该从哪里开始修？

但是，分支本身不能让系统运行，也不会自动拥有域名、数据库、账号、服务器和网络。即使仓库里已经有了 `release/1.4.0`，只要没有经过构建和部署，测试人员仍然没有地方可以验证它。

这就是环境要解决的问题。

## 环境是给不同阶段和不同角色准备的

环境的核心作用，是**把不同阶段和不同角色隔离开**，那按角色划分应该有：

- 开发人员需要一个可以频繁修改、随时重启的地方
- 测试人员需要一个相对稳定、能重复验证的地方
- 上线前需要一个尽量接近生产的地方
- 真实用户则需要一套稳定、安全、受到严格保护的生产环境。

大家的目标不同，所以才需要不同的环境。

## 常见环境分别解决什么问题？

环境没有统一的命名标准。有的团队叫 Alpha、Beta、RC、Prod，有的团队叫 Dev、Test、Staging。名字不重要，重要的是每套环境要有明确职责。

### Local 环境

Local 就是开发人员自己的本地环境，想改什么都可以，只是自己能看到而已。一个功能在本地正常，只能说明最基本的代码路径走通了，不能说明它和团队其他人的代码、公共服务以及真实部署方式都没有问题。

### Review 环境

Review 环境是用来验证一个需求的，一条功能分支对应一套临时环境，我之前参与的 [NocoBase](https://github.com/nocobase/nocobase) 是有这种的，但想想成本可能不一定在每个团队都能做到。

它解决的问题很具体：这个需求还没有合并，但产品和测试想提前看看实际效果。比如一个页面改版、一个新流程，光看截图或者代码很难确认，就可以直接访问 Review 环境。

Review 环境用完就删，它不是每个团队都必须有，但对前端项目、Web 服务和多人并行开发很有帮助。

### Alpha/Dev 环境

Alpha 环境，有的团队叫 Dev，有的团队叫 Integration 环境，主要用来验证集成状态。

两个人在各自分支上开发时都没有问题，合在一起以后可能出现接口冲突、依赖不一致或者页面互相影响。Dev 环境就是较早暴露这些问题的地方。

因为代码会频繁合入、流水线会频繁部署，所以 Dev 环境本来就不稳定。它适合开发联调和早期验证，不太适合做正式的版本回归。今天上午测过的功能，下午可能因为别人部署了新版本而发生变化。

### Release/Test 环境

Release 或 Test 或 QA 环境主要服务测试人员，用来做功能测试、集成测试和回归测试。

它最重要**固定版本**。测试开始前，大家应该先说清楚这次测的是哪个版本、包含哪些需求，以及发现问题后修复会进入哪里。

如果测试人员上午验证的是 `1.4.0-rc.1`，下午开发没有通知就把另一个功能分支部署了上去，测试结果马上失去意义，就问你测试心态崩不崩？

测试数据也应该和生产数据隔离。测试人员需要自由创建、修改和删除数据，这些操作不能影响真实用户。

### Beta/Staging 环境

Beta 或 Staging 也叫预发布环境，它应该尽量接近 Production，包括部署方式、运行版本、网络、权限等关键因素。

Staging 主要是确定“这个版本能不能安全地进入生产”。例如：

- 正式构建产物能不能正常启动。
- 数据库变更能不能顺利执行。
- 生产需要的配置是否齐全。
- 网关、域名、权限和定时任务是否正确。
- 监控、日志和告警能不能正常工作。

### Production 环境

Production 也有简称 prod 的，反正就是生产环境，运行真实业务，服务真实用户，数据和稳定性都最重要。

进入这里的版本应该已经经过前面的验证，而且每次部署都要能追溯、能监控、能回滚。谁可以部署、什么时候可以部署、失败以后怎么办，也应该有明确规则。

## 举个栗子🌰

假设要发布 `v1.4.0`，其中有“批量导入”和“高级搜索”两个需求。

### 场景一：一个需求还没合并，产品想提前看看

开发在 `feature/export-report` 上完成了第一版，这时可以由流水线生成一个构建产物，部署到临时 Review 环境。

这里，功能分支的作用是隔离“批量导入”这次代码修改；Review 环境的作用是把它运行起来，让产品和测试可以访问。一个管代码，一个管验证，两者并不是同一个东西。

需求继续修改时，Review 环境可以部署这个分支的新版本；需求合并以后，环境可以直接销毁，但 Git 里的提交和 PR 记录仍然存在。

### 场景二：两个需求要一起联调

两个需求分别合入 `develop`，CI 构建 `develop` 的最新 Commit，并部署到 Dev 环境。

`develop` 表示下个版本当前集成了哪些代码，Dev 环境则提供接口、数据库、缓存和访问地址，让这些代码真正运行起来。开发人员在这里检查两个需求放在一起是否正常。

如果这次部署失败，`develop` 分支仍然已经包含了两个需求，但 Dev 环境可能还运行着上一次成功的版本。这也能说明，分支状态和环境状态并不等价。

### 场景三：测试介入

到了提测节点，团队确定 `v1.4.0` 的范围，创建 `release/1.4.0`，构建出 `1.4.0-rc.1`，再部署到 Release/RC 还境。

测试人员此时关心版本、功能范围和部署的时间：

```text
测试版本：1.4.0-rc.1
包含需求：批量导入、高级搜索
部署时间：2026-08-13 15:30
```

发现 Bug 以后，开发回到对应的代码线上修复，生成 `rc.2`，再把 Release 还境升级到新版本。测试环境可以重复使用，但里面运行的版本一直在变化。

### 场景四：预发布

正式版本通过测试以后，创建 `v1.4.0` Tag，流水线生成不可变的正式代码。它先部署到 Staging 做最后检查，通过以后再把**同一份代码**部署到 Production。

两个环境运行的是同一份应用代码，但它们仍然不同：

- Staging 连接预发布数据库，Production 连接生产数据库。
- Staging 只有内部人员访问，Production 面向真实用户。
- Staging 的资源规模可以较小，Production 要是真实用户流量。

环境之间差异有配置、数据、依赖、权限和流量，也不仅仅是维护几份不同的代码而已。

## 一个分支必须对应一个环境吗？

之所以开发人员可能会混淆也是因为这一点，在大多数情况可能是一对一，而严格说其实是不需要的，关系也可以是多对多的。

同一个分支或 Commit 可以部署到多个环境。比如 `v1.4.0` 对应的正式产物先进入 Staging，随后进入 Production；如果需要排查问题，也可以再部署到一套临时环境。

同一套环境也可以先后运行不同分支产生的版本。Test 环境今天验证 `release/1.4.0`，明天可能需要腾出一个时间窗口验证 `hotfix/1.4.1`。环境还是那套环境，只是部署内容换了。

甚至有些环境根本没有固定分支。Review 环境跟着 PR 创建和销毁；临时演示环境可以按需选择任意一个经过构建的版本。

这也是为什么不能只通过分支名判断环境状态。真正可靠的是部署记录：某个环境当前运行哪个 Commit、哪个 Tag 或哪个镜像 Digest。

## 分支触发部署，也不等于分支就是环境

很多团队会做这样的自动化：

```text
develop 有新提交  -> 自动部署 Dev
release/* 有新提交 -> 自动部署 Test
正式 Tag 创建      -> 审批后部署 Production
```

这完全没有问题，而且是很常见的做法。但它表达的是一套**触发规则**，不是一一对应关系。

例如 `develop` 合并成功以后，流水线可能构建失败，那么 Dev 环境仍然运行旧版本；也可能构建成功，但部署因为网络问题失败。此时分支已经向前走了，环境却没有变化。

反过来，Production 回滚到上一个产物时，`main` 分支通常也不需要跟着回退。环境先恢复服务，代码再通过正常提交修复问题。

因此，“推送某分支会自动部署某环境”是对的，“这个分支就是这个环境”是不对的。

## 为什么不建议用 dev、test、prod 分支表示环境？

再回到开头那套流程：

```text
dev -> test -> staging -> prod
```

最大的问题，是这些分支把“代码怎么演进”和“代码部署到哪里”绑在了一起。

假设需求 A 和需求 B 都进入 `test`，测试后 A 可以上线，B 还不行。把 `test` 整体合到 `prod` 会带上 B；临时 Revert B，会让历史变复杂；只挑 A 的提交，又破坏了原来设想的逐级合并流程。

再比如，团队为了区分环境，在 `test` 分支里写测试接口地址，在 `prod` 分支里写生产接口地址。这样每次合并都要小心配置冲突，最后测试过的代码和真正上线的代码也不完全相同。

环境分支并不是绝对不能使用，但如果要用，至少不要在各分支里维护不同的业务代码和配置，也不要把合并当成部署本身。否则分支越来越多，环境状态反而越来越难说清楚。

更清楚的做法是：用 Feature、Release、Main 等分支表达代码范围；用流水线选择某个确定的产物部署到目标环境；用环境变量、配置中心和 Secret 管理各环境差异。
